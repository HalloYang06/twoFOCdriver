1. 项目总览

项目目标是做一套面向电机驱动器调试和控制验证的端到端系统。下位机运行在 STM32H750 上，负责实时 FOC 控制、采样、编码器反馈、PWM 输出和工业通信；上位机 DriverStudio 用 Qt6/C++20 实现，负责连接配置、寄存器读写、运动命令、三环参数整定、实时监控、波形和日志诊断。

Qt6 上位机连接配置、命令编排、参数整定、波形监控、日志诊断
协议层Modbus RTU、CANopen、EtherCAT CoE 接口预留
通信链路RS485、CAN、SPI-LAN9252、UART DMA
控制对象axis 状态机、三环控制、对象字典寄存器映射
功率与传感TIM1 三相 PWM、ADC2 注入采样、多摩川编码器

下位机主线

用 STM32H7 的定时器、ADC 注入转换、DMA、UART、SPI、FDCAN 等外设构建实时控制系统。核心控制链路是电流采样到 Clarke/Park 变换，再到 d/q 电流 PID、反 Park、SVPWM 和 PWM 占空比更新。

上位机主线

Qt6 应用通过统一的 SessionService 管理会话，把 Transport 和 Protocol Adapter 解耦；MotorControlService 再把“使能、启动、调参、读取反馈”翻译成寄存器命令。

工程主线

项目体现的不只是算法，而是工程化能力：分层抽象、实时中断边界、DMA/Cache 注意事项、协议一致性、硬件联调、仿真链路、测试回归和可演示 UI。

2. 可以重点展示的项目亮点

亮点一：从算法到硬件的闭环 FOC

项目没有停留在离线公式推导，而是把 FOC 拆成可运行的实时控制路径：ADC2 采样三相电流，编码器提供电角度，当前环在中断中执行，SVPWM 直接落到 TIM1 三相互补 PWM。

  • 电流环采样周期为 50 us，FOC 计算必须在高频 ISR 内完成。
  • 速度/位置外环以 1 ms 节拍执行，避免把慢环逻辑塞进 20 kHz 中断。
  • 电压幅值做限幅，降低 PID 输出过大导致的调制异常。

亮点二：业务对象化，Core 与业务分离

Core/Src 主要保留 CubeMX 外设初始化和中断转发，实际业务在 app、MC、BSP、comm 中完成。这让工程既能继续使用 CubeMX，又不会把业务逻辑散落在自动生成代码里。

  • app_axis.c 负责装配轴对象、编码器、电流采样和 PWM。
  • axis.c 管理状态机、运动请求、三环调度。
  • mc_foc.c 专注 FOC 算法本身。

亮点三：协议层不是“写死串口命令”

下位机把 Modbus 解析、对象字典和控制业务分开：comm_modbus.c 处理帧，comm_od.c 处理寄存器语义，axis 执行真实控制。这个边界让 CANopen、EtherCAT、上位机调试都能复用同一套控制对象。

  • 支持 0x03、0x04、0x06、0x10。
  • float 拆成两个 16-bit 寄存器，高字在前、低字在后。
  • 新增 EtherCAT 诊断寄存器，不破坏旧 TEST1 协议主路径。

亮点四：上位机有仿真闭环和测试覆盖

DriverStudio 默认可以用 SimulatedTransport 运行，不依赖硬件也能验证 Modbus、CANopen、会话生命周期、波形、主题和工作区保存。面试时这很有价值，因为可以现场演示 UI 与协议闭环。

  • Transport 和 Protocol Adapter 双抽象支持多总线扩展。
  • QtTest 覆盖配置序列化、协议编解码、仿真链路、工作区、主题和回归 UI。
  • 串口监视器能显示 TX/RX 原始帧，方便定位协议问题。

3.1 启动与实时调度

固件启动时先打开 FPU，再初始化 GPIO、DMA、TIM、UART、ADC、FDCAN、SPI 等外设。业务层随后接管：启动 TIM1 基准与 CH4 触发，初始化轴对象、通信对象、使能轴，并启动 TIM7 1 ms 中断。

main()
  SCB->CPACR 开启 FPU
  MX_GPIO_Init / MX_DMA_Init / MX_TIM1_Init / MX_ADC2_Init ...
  HAL_TIM_Base_Start(&htim1)
  HAL_TIM_PWM_Start(&htim1, TIM_CHANNEL_4)
  App_AxisInit()
  App_CommInit()
  App_AxisEnable()
  HAL_TIM_Base_Start_IT(&htim7)

面试讲法

“FOC 中有大量 float 计算，我在系统启动早期打开 Cortex-M7 FPU，并用 DSB/ISB 做同步。这个问题我实际遇到过 HardFault，所以项目里也沉淀了故障复盘文档。”

3.2 FOC 控制链路

采样

ADC2 注入转换采样 IN3、IN15、IN8，触发源来自 TIM1 CH4，确保电流采样与 PWM 时序对齐。

坐标变换

三相电流进入 Clarke 得到 alpha/beta，再根据电角度做 Park 得到 d/q 电流。

闭环控制

d 轴、q 轴分别做 PID，速度环输出 q 轴目标电流，位置环输出目标速度。

调制输出

反 Park 得到电压矢量，SVPWM 生成三相占空比，最终更新 TIM1 PWM。

关键点：电流环在 HAL_ADCEx_InjectedConvCpltCallback 中调用 App_AxisCurrentLoopIrqHandler，再进入 axis_current_loop_irq_handler。这个路径短、明确、没有阻塞调用，适合 20 kHz 的实时要求。

3.5 硬件与外设配置

PWM

TIM1 使用中心对齐，Period 2999，Prescaler 1，三相互补输出 CH1/2/3，死区 100，CH4 作为 ADC 触发参考。

采样

ADC2 注入转换 3 通道，外部触发为 TIM1_CC4，采样时间 2.5 cycles，分辨率 12 bit。

通信

USART3 作为 RS485/Modbus 通信，921600 baud；USART2 用于多摩川编码器，2.5 Mbps；UART4 用于 VOFA JustFloat 调试。

EtherCAT

SPI3 连接 LAN9252，配置约 60 Mbit/s；SYNC0/SYNC1 和 IRQ 通过 EXTI 进入 EtherCAT 调度。

CAN

FDCAN1 已配置，代码中保留 CAN 控制入口，为后续 CANopen 或自定义 CAN 控制做准备。

内存

关键 DMA 相关对象放到 D2 SRAM / RAM_D2 区，规避 STM32H7 上 DTCM 与 DMA 可访问性、Cache 一致性问题。

4. 通信协议与联调闭环

面试时建议把通信设计讲成“三层”：协议帧层负责收包验包，对象字典层负责寄存器语义，控制业务层负责真实动作。这说明你能把通信与控制解耦，而不是把串口解析写成一堆 if/else 直接改全局变量。

Modbus RTU

支持读保持寄存器、读输入寄存器、写单寄存器、写多寄存器。CRC 错误静默丢弃，非法功能码、非法地址、非法数量返回异常码。

0x03 0x04 0x06 0x10

对象字典

寄存器被映射到 axis 状态、目标值、PID 参数、EtherCAT 诊断数据。float 用两个 16-bit word 表示，高 16 位在基地址，低 16 位在基地址 + 1。

EtherCAT/CiA402

通过 LAN9252 接入 EtherCAT 从站栈，映射 CiA402 控制字、状态字、目标位置、速度、转矩，并支持 SYNC0 触发轴外环。

5. DriverStudio 上位机架构

DriverStudio 的核心价值在于把“现场调试动作”产品化：连接、发命令、读反馈、看波形、记录日志、查原始帧。它不是简单串口助手，而是面向电机驱动器的调试台。

ServiceSessionService、MotorControlService
Protocol AdapterModbusRtuAdapter、CanopenAdapter、EthercatCoeAdapter
TransportSerialRtu、CAN、EtherCAT、Simulated
DeviceSTM32H7 FOC 控制器或仿真设备

5.1 会话服务

SessionService 持有一个 transport 和一个 protocol adapter，负责 start/stop、sendCommand、超时重试、错误传播、原始帧观察。它让 UI 不需要知道底层是串口、CAN 还是仿真。

SessionService::start(config, simulationMode)
  TransportFactory::create(config.busType, simulationMode)
  ProtocolAdapterFactory::create(config.busType)
  transport->open(config)

5.2 电机控制服务

MotorControlService 用 ModbusMotorProtocolProfile 把业务动作翻译成寄存器读写。例如 Start Motion 会依次写控制模式、目标位置、目标速度、目标电流、加减速、运行时间，最后写启动寄存器。

startMotion()
  buildStartMotion()
  executeBatch()
  session.sendCommand()
  更新寄存器缓存

5.3 协议适配

ModbusRtuAdapter 负责构帧、CRC、解析响应、异常码映射，还能从噪声 buffer 中提取有效 Modbus 帧。这个处理让现场串口数据不干净时更容易诊断。

5.4 仿真链路

SimulatedTransport 内置 Modbus 寄存器和 CANopen 对象字典，支持读写回环、PDO 数据变化和 EMCY 故障。这样上位机 UI、协议和业务服务可以在没有硬件时跑通。

7. 明天演示流程建议

按这个顺序演示，逻辑会比较稳：先讲架构，再看代码，再跑上位机，最后讲问题复盘和改进计划。

7.1 代码演示路径

  1. 打开 Core/Src/main.c，展示 FPU、外设初始化、App_AxisInit、App_CommInit、TIM7 启动。
  2. 打开 app/app_axis.c，展示轴对象如何绑定 Tamagawa 编码器、ADC2、TIM1 PWM、RAM_D2 电流采样对象。
  3. 打开 MC/axis.c，展示 axis_current_loop_irq_handler 和 axis_outer_loop_handler。
  4. 打开 MC/mc_foc.c，展示 FOC 算法链路和 PID 参数。
  5. 打开 comm/protocol/comm_od.c，展示寄存器如何映射到控制变量。
  6. 切到 F:/DriverStudio，展示 SessionService、ModbusMotorProtocolProfile 和 UI 面板。

7.2 上位机演示路径

  1. 启动 DriverStudio，先选择仿真模式，连接 RS485。
  2. 进入仪表盘，说明 250 ms 刷新遥测。
  3. 进入电机控制面板，执行使能、写目标、启动运动。
  4. 进入诊断面板，输入 readi 0x0101 2 查看位置反馈原始帧。
  5. 进入波形页面，展示速度、位置、电流通道。
  6. 如果硬件在线，再切真实串口，读取一个反馈寄存器即可。

7.3 可以直接背的开场

我的项目是一套 STM32H7 FOC 电机控制器和 Qt 上位机调试平台。固件侧我重点做了三环控制、实时采样、PWM 输出、编码器反馈和 Modbus/EtherCAT 通信映射；上位机侧我做了多总线会话抽象、协议适配、运动控制面板、仪表盘、波形和诊断工具。这个项目的特点是端到端：既能讲控制算法，也能讲嵌入式实时问题和上位机工程化。

10. 常见追问回答

Q：为什么电流环要放在 ADC 注入转换完成回调里？

A：因为电流采样必须和 PWM 周期对齐，ADC 注入转换由 TIM1 CH4 触发，采样完成后立即计算 FOC，可以减少采样到输出更新之间的抖动。速度和位置环频率低，所以放到 1 ms 定时器节拍里。

Q：H7 上 DMA 和 Cache 遇到过什么坑？

A：STM32H7 有 DTCM、D2 SRAM、AXI SRAM 等区域，DMA 并不能访问所有内存；同时 DCache 会导致 CPU 看到旧数据。因此我把关键 DMA 对象放在可访问 SRAM，并在 UART DMA 等路径上关注 cache clean/invalidate。

Q：上位机为什么不直接写串口？

A：直接写串口会把 UI、协议和链路耦合死。现在用 Transport + Protocol Adapter + Service 分层，后续切 CAN、EtherCAT 或仿真链路时，UI 和业务服务基本不用改。

Q：这个项目最能体现你的工程能力在哪里？

A：我认为是闭环能力：能从控制算法写到中断和外设，从协议映射写到上位机工具，还能通过仿真和测试保障功能。它覆盖了嵌入式实时性、硬件联调、通信协议和桌面软件工程。

Q：如果让你继续完善，你会先做什么？

A：我会先统一协议枚举和单位，补充端到端联调测试；然后做 EtherCAT 主站验收和 SYNC0 周期测量；最后把 DriverStudio 的参数组、阶跃响应和调参记录沉淀成可导出的报告。

Q：为什么要做仿真链路？

A：上位机开发不能每次都依赖真实硬件。仿真链路可以验证 UI、协议、命令批处理和回归测试，还能让演示更稳定。真实硬件接入时，只需要切换 Transport。
